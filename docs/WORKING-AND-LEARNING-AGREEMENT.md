# ข้อตกลงการสร้างและเรียนรู้ VeriForge

วันที่เริ่ม: 21 กันยายน 2026

## การเปลี่ยนแปลงล่าสุด — สร้างให้ครบก่อนสอน

ผู้ใช้ยืนยันให้ทำ VeriForge v1 ให้ครบก่อน แล้วค่อยสอนจากระบบที่เสร็จแล้ว ข้อกำหนดนี้มีลำดับเหนือรูปแบบสอนทีละวงจรด้านล่าง พัฒนาต่อเนื่อง ไม่หยุดรอแบบฝึก บันทึก walkthrough/หลักฐานไว้สอนภายหลัง และยังไม่อนุมานว่าผู้ใช้เข้าใจเพียงเพราะระบบเสร็จ

## 1. เป้าหมายที่ต้องรักษาข้ามการสนทนา

ผู้ใช้ต้องการทำโปรเจกต์ให้เสร็จเร็ว แต่เข้าใจพื้นฐาน หลักการทำงาน ฟังก์ชันสำคัญ วิธีตรวจสอบ และกระบวนการทั้งระบบ ไม่ต้องการนั่งพิมพ์โค้ดทีละบรรทัดเป็นเดือน และไม่ต้องการอธิบายความต้องการเดิมใหม่ทุกครั้ง

ให้ผู้ช่วยรับผิดชอบ implementation ส่วนใหญ่ ควบคู่กับการสอนจากโค้ดที่รันได้จริง ผู้ใช้ฝึกอ่าน flow คาดการณ์ผล ทดลองเปลี่ยนพฤติกรรมเล็กน้อย และใช้ tests พิสูจน์ความเข้าใจ

ผลิตภัณฑ์เป้าหมายคือ VeriForge: ระบบตรวจสอบ AI-generated changes ที่แยก Builder, Verifier, deterministic gates, approval และ deployment พร้อมเก็บ evidence ตั้งแต่ requirement จนถึง runtime/recovery ใช้ FinTech sandbox เป็นกรณีหลัก โดยยังไม่ใช้เงินจริง

เริ่มด้วย GitHub, Python/FastAPI, PostgreSQL, Docker และ deployment target เดียว ใช้ modular monolith และ worker ก่อนขยายไป microservices เลือกบริการฟรีหรือมีค่าใช้จ่ายต่ำและคาดการณ์ได้

## 2. สร้างและเรียนไปทีละวงจร

แต่ละวงจรต้องมีปัญหาที่อธิบายได้ ผลที่สังเกตได้ และวิธีพิสูจน์ความถูกต้อง เช่น:

```text
คำขอชำระเงิน → บันทึก payment/fee → response timeout
→ client retry → พบ fee ซ้ำ → แก้ idempotency
→ รันทดสอบ → เก็บ evidence → deterministic decision
```

ไม่ต้องสอน Python หรือ cloud ทั้งหมดก่อนเริ่ม ให้สอนพื้นฐานเมื่อจำเป็นกับวงจรนั้น เชื่อมกลับไปภาพรวมเสมอว่ากำลังอยู่ตรงไหนและข้อมูลจะไปไหนต่อ

แยกสถานะสองเส้นทาง:

- **Engineering:** ยังไม่เริ่ม / กำลังทำ / รันทดสอบผ่าน / ใช้งานใน pilot แล้ว
- **Learning:** ยังไม่สอน / อธิบายแล้ว / ทดลองแล้ว / ผู้ใช้อธิบายหรือปรับเองได้

การเขียนเสร็จไม่เท่ากับผู้ใช้เข้าใจ ห้ามทำเครื่องหมายว่าเข้าใจโดยไม่มีหลักฐานจากผู้ใช้

## 3. รูปแบบหนึ่งรอบการทำงาน

| ขั้น | ผู้ช่วยทำ | ผู้ใช้ทำ | ผลส่งมอบ |
| --- | --- | --- | --- |
| 1. เปิดภาพรวม | อธิบายปัญหาและ input/output พร้อม flow สั้น | อ่านหรือถามจุดไม่เข้าใจ | รู้ว่ารอบนี้แก้อะไร |
| 2. สร้าง | เขียนส่วนเล็กที่รันได้ รวม validation ที่จำเป็น | ไม่ต้องพิมพ์ตาม | โค้ดและวิธีรัน |
| 3. พาอ่าน | เดินตาม request ผ่านไฟล์/ฟังก์ชันสำคัญ | เปิดตามหรืออ่าน lesson ภายหลัง | Code walkthrough |
| 4. ทำให้พัง | เตรียม fault ที่ปลอดภัยและระบุผลคาดหวัง | ทายผลก่อนทดลองถ้าพร้อม | เห็น failure จริง |
| 5. แก้และพิสูจน์ | อธิบายทางแก้และรัน tests ที่ตรวจ behavior | ทดลองแก้จุดเล็กตามสมัครใจ | ผลเปรียบเทียบก่อน/หลัง |
| 6. บันทึก | อัปเดต lesson, evidence และ progress | ตอบ teach-back เมื่อสะดวก | กลับมาต่อได้โดยไม่เริ่มใหม่ |

เวลาเรียนต่อวงจรตั้งต้นประมาณ 20–40 นาที ปรับตามความพร้อม ไม่ใช่คำรับประกันเวลาพัฒนา ระบบสามารถพัฒนาต่อในส่วนที่ได้รับอนุญาตแม้ผู้ใช้ยังไม่ทำแบบฝึก

## 4. สิ่งที่ต้องอธิบายสำหรับฟังก์ชันสำคัญ

แต่ละฟังก์ชันที่เกี่ยวกับเงิน สิทธิ์ state transition evidence policy หรือ deployment ต้องมีคำอธิบายอย่างน้อย:

1. **Purpose:** แก้ปัญหาอะไร ทำไมต้องมี?
2. **Caller:** ใครเรียก ผ่าน API/job/event ใด?
3. **Input:** ชนิดข้อมูล ตัวอย่าง validation และข้อมูลที่ไม่ควรเชื่อถือ
4. **Output:** ค่าที่คืน สถานะ error และ contract ที่ caller พึ่งพา
5. **Dependencies:** เรียกอะไรต่อ อ่าน/เขียนตารางหรือ service ใด?
6. **Side effects:** เปลี่ยน state ส่ง event เรียก external API หรือใช้เงิน/เวลาอย่างไร?
7. **Invariant:** เงื่อนไขที่ต้องเป็นจริงก่อนและหลังการทำงาน
8. **Identity:** ใครมีสิทธิ์เรียก และตรวจสิทธิ์ตรงไหน?
9. **Concurrency:** สองคำขอพร้อมกันหรือ retry จะเกิดอะไร?
10. **Failure:** หยุดกลางทาง/timeout/dependency ล่มแล้วข้อมูลอยู่สภาพไหน?
11. **Evidence:** test ไหนตรวจพฤติกรรมนี้ และดูผลจากที่ไหน?
12. **Trade-off:** วิธีนี้มีข้อจำกัดอะไร และเมื่อไรควรเปลี่ยน?

แยกหัวข้อที่ไม่เกี่ยวข้องด้วยคำว่า “ไม่เกี่ยวข้อง เพราะ…” แทนการแต่งเหตุผล สำหรับ helper ง่าย ๆ อธิบายสั้นได้ ไม่ต้องทำคำอธิบายยาวทุกบรรทัด ให้เอกสารเน้นเหตุผลและ failure boundaries ส่วน syntax ที่ไม่คุ้นอธิบายเมื่อพบ

## 5. สไตล์การสอน

- ใช้ภาษาไทย คงชื่อ technical terms และอธิบายเป็นคำง่ายเมื่อเจอครั้งแรก
- เริ่มจากพฤติกรรมที่มองเห็น → flow → code → test → trade-off
- ยกตัวอย่าง input/output จริง ไม่อธิบายด้วยคำจำกัดความอย่างเดียว
- ใช้ภาพหรือตารางเมื่อช่วยให้เข้าใจ ownership, state หรือ sequence ได้ดีขึ้น
- ลิงก์ไปไฟล์จริงและชื่อฟังก์ชันจริง ถ้าโค้ดยังไม่มีให้ระบุว่าเป็นแบบร่าง
- แยก “เพราะหลักการบังคับ” กับ “ตัวเลือกที่เราเลือกเพื่อประหยัด/ลดความซับซ้อน”
- อย่าใช้คำว่า secure, production-ready, exactly-once หรือ independent โดยไม่อธิบายขอบเขตและหลักฐาน
- หลีกเลี่ยงโค้ดก้อนใหญ่ที่ไม่มี walkthrough และการทดสอบความเข้าใจที่ยืดยาว

## 6. แบบฝึกที่ใช้เวลาน้อยแต่ได้คิด

ให้หนึ่งโจทย์เล็กต่อรอบ เช่น ส่ง idempotency key เดิมแต่เปลี่ยน amount, ตัด permission หนึ่งรายการ, ทำ scanner timeout หรือเพิ่ม test ของ cross-tenant request ผู้ใช้ควรทายผล อธิบายเหตุผล แล้วเทียบกับผลจริง

คำถาม teach-back ใช้เพียง 2–3 ข้อ เช่น “ทำไม status check อย่างเดียวไม่พอ?”, “ถ้า crash หลัง commit จะ retry อย่างไร?”, “test ที่ผ่านนี้ยังไม่ได้พิสูจน์อะไร?” หากผู้ใช้ยังไม่ตอบ ให้บันทึกว่า pending ไม่ใช่ failed และไม่หยุดงานที่ทำต่อได้

ความเข้าใจขั้นต่ำของ module คือผู้ใช้อธิบายเส้นทางข้อมูล จุดบังคับกฎ failure สำคัญ และปรับพฤติกรรมเล็ก ๆ พร้อมทดสอบได้ ไม่จำเป็นต้องจำ syntax ทุกคำ

## 7. ข้อมูลจริงและการวัดผล

ใช้ labels `REAL_OPERATIONAL`, `PUBLIC_BENCHMARK`, `SYNTHETIC_REPLAY`, `INJECTED_FAULT` ให้ชัดเจน Dataset สาธารณะไม่เท่ากับข้อมูลธุรกรรมจริงเสมอไป PaySim เป็น synthetic; SWE-bench ไม่ได้พิสูจน์ end-to-end finance assurance; provider sandbox ไม่ได้เคลื่อนเงินจริง

ทุก experiment เก็บ source/version/checksum, transformation, seed, hardware, software versions, commit/artifact, workload, sample size, raw output และ metric definition บันทึกการตัดข้อมูลและข้อจำกัด ห้ามใส่ KPI hardcode ให้ดูเหมือนผลจริง

การตรวจต้องใช้ specification, trusted tests และมนุษย์ตรวจ label ตามความเหมาะสม ไม่ให้ AI ที่ถูกประเมินเป็นผู้ตัดสินความถูกต้องของตัวเองทั้งหมด แยก evaluation set จาก development และระบุ benchmark contamination risk

## 8. หลักประหยัดเวลาและเงิน

- ทำหนึ่ง vertical slice ให้ครบก่อนเพิ่ม service/framework
- ใช้ local environment และ deterministic checks ก่อน paid model/cloud
- ใช้ baseline ที่เรียบง่าย แล้วเพิ่ม complexity เมื่อผลวัดหรือ requirement บังคับ
- ไม่ต้องรันทุก scanner ทุกครั้งที่แก้เอกสาร เลือก validation ตามความเสี่ยง
- Tests ควรพิสูจน์พฤติกรรมหรือ failure จริง ไม่ mirror implementation
- กำหนด AI retries, token/job budget, concurrency และ monthly cap ก่อนเปิด automation
- งาน auth, trusted controls และ backup ไม่ถูกเลื่อนไปเพียงเพราะเป็น demo

## 9. วิธีเริ่มครั้งถัดไป

เปิด workspace ที่ `my-pj/VeriForge` เพื่อให้ `AGENTS.md` อยู่ในขอบเขตของงาน แล้วพิมพ์สั้น ๆ ว่า “เริ่มต่อ” หรือ “เริ่มบทแรก” ก็เพียงพอ ไม่ต้องทวน requirement ทั้งหมด

ผู้ช่วยอ่าน agreement และ progress ตรวจสภาพไฟล์จริง แล้วบอกสั้น ๆ ว่าทำถึงไหน จะทำอะไรต่อ และบทเรียนเกี่ยวข้องกับอะไร หากเปิด workspace ที่กว้างกว่าและระบบไม่ได้อ่านไฟล์ลูกอัตโนมัติ ให้ชี้ไป `VeriForge/AGENTS.md` หนึ่งครั้ง ไม่อ้างว่าจำได้ทุกแชตโดยไม่อ่านไฟล์

ก่อนจบทุก session อัปเดต progress พร้อม next action ที่ทำได้ทันที หากมี blocker ให้ระบุสิ่งที่ตรวจแล้วและข้อมูลที่ขาด ไม่สร้างผลตรวจที่ไม่ได้รัน

## 10. ขอบเขตเอกสารนี้

นี่คือ workflow และบริบทถาวรของโปรเจกต์ ไม่ใช่คำอนุญาตให้ซื้อบริการ ส่งข้อความภายนอก publish หรือ deploy โดยอัตโนมัติ คำขอปัจจุบันและสิทธิ์ที่มีอยู่กำหนดสิ่งที่จะลงมือ หากผู้ใช้ถามหรือขอเอกสารอย่างเดียว ให้ทำตามนั้น
